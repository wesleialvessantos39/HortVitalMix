## Implementação entregue

### Seleção explícita de ambiente
A mesma base de código suporta:
- `development`;
- `homologation`;
- `production`.

A resolução ocorre nesta ordem:
1. `HORTIVITALMIX_ENV` / `APP_ENV` quando explicitamente definido;
2. `VERCEL_ENV=development|preview|production`, com `preview -> homologation`;
3. ambiente local sem variável -> `development`.

Valor explícito inválido interrompe a inicialização; não há fallback silencioso para production.

### COR 05 — porta vazia
`API_PORT` e `PORT` vazios são ignorados e a API usa a porta segura local 3001.
Valor não vazio inválido encerra a inicialização em vez de produzir porta `NaN`.

### Banco por ambiente
O runtime usa exclusivamente `DATABASE_URL`.
Migrações usam exclusivamente:
- `MIGRATION_ENV`, obrigatório;
- `DATABASE_MIGRATION_URL`, obrigatório.

O migration runner não reutiliza `DATABASE_URL`, impedindo que credencial de runtime seja usada silenciosamente para migração.

### Identidade do banco e prevenção de fallback
A migration `0003_oe_001_003_environments.sql` cria `app_releases`.
Cada banco possui exatamente um release corrente com:
- ambiente;
- versão;
- commit SHA;
- referência do artefato.

`/api/ready` somente retorna ready quando:
1. PostgreSQL responde;
2. há release corrente;
3. o ambiente gravado no banco é igual ao ambiente selecionado no runtime.

Se homologation for ligado ao banco production, a API retorna 503 com `databaseBinding=mismatch`; ela não aceita o banco errado como fallback.

### Correção pós-homologação — preview Google AI Studio
Foi identificado no Google AI Studio que o frontend abria, porém a aplicação caía em **“Não foi possível consultar a API do HortiVitalMix”**.

Causa confirmada no código: o Vite encaminhava `/api` para um segundo processo em `localhost:3001`. Esse modelo funciona em uma estação local com os dois processos ativos, mas não é confiável no preview de processo único do Google AI Studio.

Correção aplicada:
- removido o proxy obrigatório para `localhost:3001`;
- o Vite em modo `serve` agora monta a **mesma instância Express canônica** de `server/app.ts` no mesmo processo;
- `npm run dev` passa a iniciar frontend + backend juntos no mesmo servidor;
- removida a dependência `concurrently`, que deixou de ser necessária para o fluxo principal;
- o pool PostgreSQL é encerrado quando o servidor Vite fecha;
- sem `DATABASE_URL`, a apresentação carrega com configuração default segura, enquanto readiness continua 503 e nenhuma persistência é simulada;
- o comportamento Vercel permanece separado e inalterado, usando `api/index.ts`.

Teste de integração adicionado em `tests/integration/google-ai-studio-preview.test.ts`, comprovando que os três endpoints usados no boot (`config`, `health`, `environment`) respondem sem variáveis e que readiness não finge banco pronto.
