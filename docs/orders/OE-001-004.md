## Decisão sobre a referência à divergência 0014
A OE-001-004 do Manual v6 exige resolver primeiro a divergência histórica da migração 0014 e proíbe corrigir o problema sobrescrevendo checksums ou reexecutando SQL em produção.

O repositório greenfield atual e os três bancos Neon canônicos foram inspecionados antes da alteração. Neste projeto iniciado do zero:
- o histórico canônico continha exclusivamente as versões 1, 2 e 3;
- nenhum arquivo `0014_*.sql` existe no repositório greenfield;
- nenhum dos bancos development, homologation ou production possuía versão 14 no `app_schema_migrations`;
- os nomes e checksums das versões 1–3 coincidiam entre GitHub e os três ambientes.

Portanto, a divergência 0014 pertence ao histórico legado que originou a regra do Manual, mas **não existe como estado aplicado neste greenfield**. Importar a migração legada ou fabricar um checksum seria recriar exatamente o problema que o Manual manda evitar.

A reconciliação aplicada nesta base é:
1. preservar integralmente os arquivos 0001–0003 já aplicados;
2. manter um manifesto imutável de versão + nome + SHA256;
3. rejeitar qualquer versão remota inesperada, inclusive uma eventual versão 14;
4. nunca atualizar checksums aplicados para “forçar” concordância;
5. adicionar novas mudanças somente como migration 0004 e posteriores.

## Runner de migrations
Foram adicionados:
- `shared/database/migrationManifest.ts`;
- `server/db/migrationIntegrity.ts`;
- `scripts/migrationRunner.ts`;
- `scripts/verifyDatabase.ts`.

### Regras do runner
- lê os bytes integrais UTF-8 de cada SQL;
- calcula SHA256 sem normalizar conteúdo;
- compara quantidade, versão, nome e checksum com o manifesto;
- bloqueia edição de arquivo já aplicado;
- lê o histórico remoto antes de aplicar qualquer nova migration;
- rejeita versão remota inesperada, lacuna, nome divergente ou checksum divergente;
- usa advisory lock de sessão;
- executa cada migration em transação;
- só registra `app_schema_migrations` após o SQL concluir;
- verifica novamente o histórico remoto depois da execução;
- exige `MIGRATION_ENV`, `DATABASE_MIGRATION_URL` e `MIGRATION_COMMIT_SHA`;
- não usa silenciosamente `DATABASE_URL` de runtime para migração;
- registra release corrente com ambiente, commit SHA, schema version e hash do histórico.

Comando de conferência:
`npm run db:verify`.

1. criava `app_oe001004_atomicity_probe`;
